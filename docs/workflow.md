# UNSEEN 협업 흐름

팀 기준은 작업 정의 → 작은 변경 → 검증 근거 → PR → 다른 팀원 리뷰다.

## 브랜치 규칙

| 브랜치 | 역할 |
| --- | --- |
| `dev` | 작업 PR을 모아 함께 검증하는 개발 브랜치 |
| `main` | 검증을 마친 데모·제출 기준 버전을 보관하는 브랜치 |
| `feat/private-records`, `fix/screen-state`, `docs/team-workflow` | `dev`에서 시작하고 `dev`로 PR을 여는 작업 브랜치 |

작업 브랜치는 `type/short-description` 형식으로 짓고, 영문 소문자와 하이픈을 사용한다. 사람과 AI 에이전트에 같은 규칙을 적용하며 브랜치명에 `codex`, `claude` 등 도구 이름을 붙이지 않는다. `dev`와 `main`에는 PR을 통해 반영한다.

## 작업 시작

1. 작업 전 `git status`와 현재 브랜치·기존 변경을 확인한다. 최신 기준은 팀이 머지한 앱 저장소다.
2. [작업 목록](../tasks/README.md)에서 중복·의존 작업을 확인한다. 기능·SDK·여러 파일 작업은 [작업 양식](../templates/task.md)을 복사하고 담당자·완료 조건·수정 범위를 적는다.
3. 최신 `dev`를 기준으로 작업 브랜치를 만든다. 같은 작업·파일을 동시에 맡으면 먼저 범위를 조정한다.
4. 요구는 [제품 기획](../intent.md), 열린 선택은 [결정 기록](decisions.md), SDK는 [Pleos 조사](pleos.md)와 최신 공식 문서에 연결한다.

작은 문서 수정에 별도 양식 다섯 개를 만들 필요는 없다. 이슈·작업 문서·PR에 중복 기록하기보다 하나의 상세 근거를 링크한다.

## 구현·검증

- 요청 범위를 구현하고 기존 사람·AI의 변경을 보존한다. 다른 팀원의 브랜치를 강제 갱신하지 않는다.
- 동작 변경은 [UNSEEN 시나리오](verification-scenarios.md)에서 관련 정상·실패·복귀·개인정보 항목을 선택한다.
- 실제 수행한 명령·환경·결과를 작업/PR에 남긴다. 상세 기록은 [검증 양식](../templates/verification.md)을 쓴다.
- 문서 검사, 단위 로직, Android build, SDK 호출, Emulator 시나리오를 별도로 보고한다. 합성 경로·Mock 데이터는 명시한다.

| 상태 | 의미 |
| --- | --- |
| PASS | 실행했고 기대 결과 확인 |
| FAIL | 실행했으나 기대 결과 불충족 |
| NOT_RUN | 아직 실행하지 않음 |
| BLOCKED | 입력·환경·권한이 없어 수행할 수 없음 |
| NOT_APPLICABLE | 해당 작업과 관련 없음 |

## 커밋 규칙

새 커밋의 제목은 `type(scope): 변경 요약`으로 쓴다. 범위가 하나로 좁혀지지 않으면 `type: 변경 요약`으로 쓴다. `type`과 `scope`는 영문 소문자를 쓰고, 요약은 한국어 또는 영어 한 줄로 무엇이 바뀌었는지 적는다. 범위는 `app`, `pleos`, `harness`처럼 변경 영역을 나타낸다.

| 유형 | 언제 쓰는가 |
| --- | --- |
| `feat` | 기능 추가 또는 확장 |
| `fix` | 기존 동작의 오류 수정 |
| `refactor` | 동작을 유지하는 코드 구조 개선 |
| `docs` | 문서만 변경 |
| `test` | 테스트 추가 또는 수정 |
| `build` | Gradle, 빌드 설정, 의존성 변경 |
| `ci` | CI 설정 또는 파이프라인 변경 |
| `chore` | 그 외 저장소 유지보수 |

- `feat(app): 개인 기록 화면 추가`
- `fix(app): 화면 회전 후 현재 화면 복원`
- `docs(harness): 커밋 규칙 정리`

한 커밋에 하나의 변경 목적을 담는다. 기능과 그 기능에 필요한 테스트·문서는 함께 묶고, 별개 목적의 변경은 나눈다. 커밋 전에 `git diff --cached`로 대상과 내용을 확인한다. 제목만으로 변경 이유를 파악하기 어려우면 빈 줄 뒤 본문에 이유와 필요한 제약을 적고, 관련 이슈가 있으면 `Refs #123`처럼 연결한다.

## 공유와 리뷰

1. 문서 검사와 작업별 검증 후 자신의 변경만 선택해 커밋·푸시한다. 로컬 파일만 만들어서는 팀원에게 전달되지 않는다.
2. 작업 브랜치에서 `dev`로 PR을 연다. 문제·결과·작업 링크·검증과 한계를 적고 다른 팀원에게 리뷰를 요청한다. [PR 양식](../.github/pull_request_template.md)을 사용한다.
3. 팀 리뷰 후 `dev`에 머지한다. 팀원은 작업 트리를 정리한 뒤 최신 `dev`를 받는다. 미커밋 변경을 강제로 덮어쓰지 않는다.
4. 데모·제출 버전을 확정할 때 `dev`에서 `main`으로 PR을 열고, 후보 버전의 검증 결과를 검토한 뒤 머지한다.

## 앱 검증과 배포

- 앱 모듈 추가 후 [로컬 빌드·Lint](environment.md)와 관련 Pleos 에뮬레이터 시나리오를 실행해 PR에 기록한다. UI와 화면 흐름은 명시한 Mock 데이터로 검증할 수 있다.
- 반복 검증을 자동화할 때는 GitHub Actions의 PR 검사부터 시작한다. 후보는 문서 검사, 디버그 빌드, Lint다. Pleos 기능은 해당 환경에서 에뮬레이터·실차 확인을 따로 기록한다.
- 배포 자동화는 제출 방식과 서명 절차가 정해진 뒤 별도 작업으로 검토한다. PR 절차와 승인·검사 강제 설정은 GitHub 브랜치 보호에서 관리한다.

## 인수인계와 결정

- AI 도구·담당자를 바꿀 때 [인수인계 양식](../templates/handoff.md)에 branch·commit·현재 변경·남은 일·첫 다음 행동을 적는다.
- 개인 채팅의 결론은 공유 기록에 옮긴다. 역할·기술·데이터 정책 변경은 결정자·날짜·근거를 남긴다.
- 이 저장소가 UNSEEN 규칙 원본이다. 이전 하네스의 변경이 자동 반영된다고 가정하지 않는다.
